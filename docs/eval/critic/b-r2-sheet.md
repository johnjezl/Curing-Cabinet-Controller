# Behavior sheet: hardware-driver and provisioning layer

Source: one fresh run on the actual board, 2026-11-07 02:41:37Z to 02:52:58Z, 681 s, script exit 0, plus four one-off captures not regenerated by that run. No sensor, relay, load, fan or measuring instrument was attached in any capture. All line and fan-pin figures are the board reading its own GPIO registers. Where a figure has outputs on, a test driver was deliberately holding them on and the capture says so; the control application was not driving them.

- Item R1.7: No sensor reading was ever obtained on the board, so resolution and probe-inclusive error are unknown. Every temperature/humidity read returned an error with value 0.0 C / 0.0 %. No reference instrument or comparison exists. Unit tests with a fake device pass for pulse decoding, but their output shows only names and PASS, with no resolution or error figure. (NOT-SHOWN)
- Item R1.8: No calibration offset appears in any capture, and none of the 81 test names covers one. (NOT-SHOWN)
- Item R3.5: On the board with no relays or load attached, and a test driver holding 6 lines on: control loop stuck with process alive, all lines low at 2808-2848 ms (3 runs); control process frozen, 2811 ms (3 runs); control process killed, 0.25-2.17 ms (3 runs); output guard frozen, 2111-2200 ms (3 runs); output guard killed, 7.4-10.8 ms (3 runs). There were no high samples in the next 1500 ms in any of the 15 runs. The alarm and buzzer lines drop along with the others. The fan pin stayed at about 25 kHz and 50 % in 15 of 15 runs, so the fan keeps its last command after control or guard death. The 3 s lease does not depend on temperature validity: no capture shows outputs reacting to a lost temperature reading while control keeps renewing the lease. (MEASURED-RIG)
- Item R4.1: Only a sensor that was never attached was exercised; no transition from good reading to lost reading happened on the board. First read returned "no reading yet: device absent" in 450.7 ms (450.7 ms in the second run; bound 500 ms). Later reads returned "device absent ... connection timed out" in 0.010-0.014 ms, value 0.0 C. Fake-device tests with names covering stale-sample expiry pass, but the expiry time is not printed. Time from loss of a live sensor to report is unknown. (MEASURED-RIG)
- Item R4.2: Humidity arrives in the same read call as temperature, with the same figures: 450.7 ms first read, about 0.01 ms afterwards, value 0.0 %, with no sensor ever attached. No separate humidity-only failure was exercised, and the captured error text names the temperature channel only. Time from loss of a live humidity reading to report is unknown. (MEASURED-RIG)
- Item R4.4: No sensor recovery was exercised on the board because no sensor was ever present, and no test name explicitly covers a read fault clearing after recovery. The only clearing shown is a different fault: after an unsafe kernel parameter was set back, the guard logged "safety precondition restored" and a commanded line went high again on the next request. (NOT-SHOWN)
- Item R4.5: Installed binaries and service files had unchanged hashes before and after 1 graceful reboot and 2 unclean resets in the run. Services, overlays and PWM setup (40000 ns period, duty 0) came back after those resets and after 2 power cuts (labelled 3 s and 60 s, n=1 each, one-off captures). Boot-record sequence numbers run 1-36 without a gap across 22 unclean boots, 5 of them with the power-on reset flag. Provisioning reported changed=0 only after the graceful reboot; it was not rerun after a panic or power cut. No application configuration content is listed or compared, so configuration survival is not shown. No control application unit existed after any of these resets (not-found). No filesystem check result is shown. (MEASURED-RIG)
- Item R4.6: The clock does not survive power loss on this bench. After both power cuts the board clock read 1970-01-01T00:00:12 at kernel start, and boot records hold rtc=47-50 at about 35 s uptime. The system clock then came from an earlier saved time until network time arrived, and boot-record stamps came out 76 s and 124 s behind real time, earlier than the power cut itself by 20 s and 15 s. Network time was present for all runs; behavior without it was not exercised. Across panic and graceful reboot the board clock held. (MEASURED-RIG)
- Item R4.9: Shown on the board: a boot record with clean/unclean class, reset flags and clock figures per boot; the guard refusing outputs and logging when an unsafe kernel parameter is set; service-manager log lines for guard watchdog kills; journal "corrupted or uncleanly shut down" warnings. Reset flags read 0x20 for reboot, panic and the watchdog-style test alike, and 0x1020 for a reboot that follows a power cut. The kernel crash store was empty after a panic. Storage write failure, full disk and corrupt configuration were not exercised. All of these reports are log or file entries only; no capture shows one reaching an operator. (MEASURED-RIG)
- Item R4.10: No detection of a plausible but wrong reading is shown. Bad-read rejection exists only in fake-device tests, by name: bad pulse trains, bad checksum, bus-rail frames, saturated ADC, implausible fan speed. The bad-read flag was never true in any board capture. No redundant sensor, cross-check or stuck-value test appears. (NOT-SHOWN)
- Item R4.11: No rating statement or independent hardware cutoff appears in any capture. No load, relay or external instrument was attached, and the test driver held outputs on. Process crash and hang figures are under R3.5. Kernel panic with 1 s reboot: new kernel 10.0 s after command, all 6 lines low and fan pin at 0 edges at first read 44.2 s after command, n=1. Capture named as watchdog-only reset: new kernel 17.9 s after command, lines low at first read 51.1 s after command, n=1. Power cut: lines low at first read 54.6 s and 107.6 s after the last ping, n=1 each. Those three figures are first-look times and not time-to-safe, because nothing observed the lines between command and first read. Before bring-up, at 33-37 s uptime after unclean boots and 15 s after a graceful one, the lines show no function with pull-down. The hardware watchdog (10 s) is armed at about 19-20 s of kernel time after unclean boots and 2.7 s after a graceful one. A hung kernel other than the panic tests, a hung init process, brownout, and multi-day running were not exercised. (MEASURED-RIG)
